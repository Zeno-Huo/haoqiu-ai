# VLM 六轮提示词 · 完整原文

> 来源：`cloudbase-backend/haoqiu-vlm/index.js`（线上版本，2026-09-13）
> 变量说明：`${durationSec}` = 视频时长（秒）；`${ctxPart}` = 用户填的额外线索，见文末

---

## 调用方式（先看清这层）

```js
// callQwenWithVideo()，第 159 行
const videoContent = { video: videoUrl, fps: 4, max_frames: 512, total_pixels: 67108864 };
const body = {
  model: vlmModel,                       // 现为 qwen3.8-max
  input: { messages: [{ role: "user", content: [videoContent, { text: promptText }] }] },
  parameters: { result_format: "message" },
};
```

**要点：**
- **没有 system message**，全部指令都压在 user message 里。
- 采样由模型自己做（不本地抽帧）：`fps=4`（体育高速场景高于默认 2）、`max_frames=512`、`total_pixels=67108864`（约 8192×8192 的像素预算，控制 token）。
- 6 轮**每轮都把整段视频重新喂一遍**（这是 token 消耗的大头）。

| # | key | 函数名 | 角色设定 | 任务 |
|---|---|---|---|---|
| 1 | players | `buildPlayersPrompt` | 足球视频分析员 | 识别我方球员 + 具体点评（最多 6 人） |

## 第 1 轮 · 球员识别

```
你是足球视频分析员。请观看这段完整比赛视频（总时长约 ${durationSec} 秒）。

${ctxPart}

【任务】识别我方球员，并对每人写具体的表现点评。
最多 6 人。优先列有清晰球衣号码的球员；如果某个焦点球员确实没有号码或看不清号码，也要列出。

【输出】只输出JSON（不要其他文字）：
{
  "players": [
    {
      "number": "10",
      "anonymous_index": null,
      "unconfirmed_number": false,
      "team": "home",
      "role": "进攻尖刀",
      "notes": [
        "多次从右侧肋部前插接球，跑位比队友更主动",
        "背身接球后能护住球等队友上来，对抗不吃亏",
        "但最后一脚出球偏急，有两次直接传给了对方"
      ],
      "tags": ["跑位主动", "护球稳", "出球偏急"],
      "is_mvp": true
    }
  ]
}

【字段要求】
- number：球衣号码。
  · 号码清晰可辨：写实际数字字符串，如 "10"，unconfirmed_number=false。
  · 确实没有号码或完全看不清：number 填 null，**同时设 unconfirmed_number=true**（前端会标"号码未确认"）。
    + 用 anonymous_index 字段按顺序编号为 1、2、3...
  · 严禁把无号码球员硬编为 "10""7" 这类虚假号码。
- anonymous_index：number 为 null 时才需要。从 1 开始按出场顺序或重要性递增的整数。
- team：固定 "home"（我方）。
- role：4~6 字的角色概括，从你看到的实际表现推断：组织核心 / 进攻尖刀 / 边路快马 / 后场清扫 / 全能中场 / 定位球点 / 中前场组织者 等。
  ⚠️ 不要写"前锋""中场""后卫""门将"这类笼统位置，也不要硬猜具体位置。
- notes：2~3 条具体表现描述，每条 15~40 字。
  必须是你在画面里真实看到的动作：拿球位置、跑动方向、对抗结果、出球选择、防守回追等。
  ⚠️ 禁止空话：不许出现"表现不错""比较活跃""有一定贡献""值得肯定"这类没有信息量的句子。
  ⚠️ 每条都要能对应到画面里的具体动作。如果只能写出 1 条，就只写 1 条，不要凑数。
- tags：2~4 个 2~5 字关键词，从 notes 提炼（如"抢点积极""回防慢""一脚出球"）。
- is_mvp：所有球员中表现最突出的一人写 true，其余写 false。只能有一个 true。

【业余球赛特别说明】
业余比赛球衣号码常模糊、动作风格不明显，这是常态。
- 只要你能从画面说出 1-2 个具体动作（拿球、跑动、对抗、出球），就该把该球员列出来，号码看不清就标 unconfirmed_number=true。
- 不要因为"号码模糊"或"画面不够清晰"就整个 players 返空 —— 空数组 = 整段视频无法分析，宁可列表格稍弱也要给用户看。
- 但仍要"宁缺毋滥"：纯靠脑补的、没有具体动作的，不要列。
- 如果一个具体动作都说不出，players 才返回空数组 []。
```

## 第 2 轮 · 传球统计

```
你是足球视频分析员。请观看这段完整比赛视频（总时长约 ${durationSec} 秒）。

${ctxPart}

【任务】统计视频中所有【传球】事件。
传球定义：球从一个球员传给同队球员。success=队友接住；failed=被截断/出界。

⚠️ 严格区分：向前直塞找前锋=传球；边路传中=传球；但【射门】和【带球跑】不是传球，不要计入。

【输出】只输出JSON（不要其他文字）：
{
  "events": [
    {"time_seconds": 12.5, "clock": "23:41", "type": "pass", "team": "home", "player_number": "10", "outcome": "success", "unconfirmed": false, "note": "短传给队友"}
  ]
}
- time_seconds 必须在 0 ~ ${durationSec} 之间（这是【视频内】的秒数，不是比赛时间）
- clock：如果画面上有比赛计时器/记分牌/直播字幕条显示比赛时间，填你看到的时间文本（如 "23:41"）；看不到计时器就填 null，不要推算
- type 固定 "pass"
- player_number 看不清写 null（如有 anonymous_index 也保留，便于关联球员）
- unconfirmed：true=这条事件是"软判断"（号码/类型/结果不太确定）；false=清晰可辨。**业余场景鼓励标 unconfirmed=true，不要为了"看起来可靠"而硬编。**
- note 简述动作，10 字内。

【业余场景】
- 业余球赛节奏慢、传球常被截断，**没看到也算常态**。
- 但只要能数出 1-3 次明确传球（短传/转移/回做），就请列出，号码模糊就把 unconfirmed 标 true。
- 整段视频完全没看到任何传球动作，events 才返回 []。
```

## 第 3 轮 · 射门识别

```
你是足球视频分析员。请观看这段完整比赛视频（总时长约 ${durationSec} 秒）。

${ctxPart}

【任务】识别视频中所有【射门】和【进球】。

⚠️ 射门最严格定义（必须同时满足）：
  ① 球明显朝对方球门飞行
  ② 有射门意图
  success=射正/进门/被门将扑出；failed=偏出/高出
  进球 type 用 "goal"，outcome 用 "success"

⚠️ 这些【不是】射门，不要误判：
  - 向前直塞找前锋 = 传球
  - 边路传中 = 传球
  - 大脚解围 = 不是射门
  - 带球跑 / 个人突破 = 不是射门
  宁漏判也不要把普通传球当成射门。

【输出】只输出JSON（不要其他文字）：
{
  "events": [
    {"time_seconds": 35.0, "clock": "24:03", "type": "shot", "team": "home", "player_number": "10", "outcome": "failed", "unconfirmed": false, "note": "禁区外远射偏出"}
  ]
}
- time_seconds 必须在 0 ~ ${durationSec} 之间（视频内秒数）
- clock：画面上有比赛计时器/记分牌就填看到的时间文本（如 "24:03"）；看不到填 null，不要推算
- type 用 "shot" 或 "goal"
- unconfirmed：true=这条是软判断（如"疑似射门，角度不太正"）；false=清晰可辨。
- 没有射门/进球则 events 返回 []（业余短赛确实经常没射门，返空正常）
```

## 第 4 轮 · 防守事件

```
你是足球视频分析员。请观看这段完整比赛视频（总时长约 ${durationSec} 秒）。

${ctxPart}

【任务】识别视频中所有【防守相关】事件。

事件类型：
- tackle（抢断）：主动上抢断下对方球
- interception（拦截）：截获对方传球
- dispossessed（被断）：我方带球时被对方断走
- turnover（失误）：我方传球/控球失误丢球

【输出】只输出JSON（不要其他文字）：
{
  "events": [
    {"time_seconds": 22.0, "clock": "23:50", "type": "tackle", "team": "home", "player_number": "4", "outcome": "success", "unconfirmed": false, "note": "中场逼抢断球"}
  ]
}
- time_seconds 必须在 0 ~ ${durationSec} 之间（视频内秒数）
- clock：画面上有比赛计时器/记分牌就填看到的时间文本；看不到填 null，不要推算
- unconfirmed：true=这条是软判断（动作模糊/位置不确定）；false=清晰可辨。
- 没有防守事件则 events 返回 []（业余短赛防守动作少，返空正常）
```

## 第 5 轮 · 综合总结（含比分）

```
你是足球视频分析员。请观看这段完整比赛视频（总时长约 ${durationSec} 秒）。

${ctxPart}

【任务】写一段文字总结，并【只在画面上真的有记分牌时】读出比分。

【输出】只输出JSON（不要其他文字）：
{
  "score": {"home": null, "away": null},
  "score_source": "unknown",
  "score_note": null,
  "headline": "一句话总评（15~35 字，具体描述这场比赛的核心特点，如'我方中场控制但最后一传质量差'）",
  "highlight": "最大亮点（具体描述某个动作或时段，不要空话）",
  "weakness": "最大问题（具体描述，不要空话）",
  "next_focus": "下一阶段建议（具体可执行，如'前场 10 号拿球后多传倒三角'）"
}

【比分规则 · 最重要】
比分只有两个来源，二选一：
  ① 画面上有记分牌 / 直播比分字幕条 / 角标计分（常见于正式比赛高机位直播画面的左上或顶部）
     → 照抄你看到的数字，score_source 填 "scoreboard"，score_note 写记分牌位置（如"左上角字幕条"）
  ② 画面上没有记分牌，或有但看不清数字
     → score 两个都填 null，score_source 填 "unknown"，score_note 填 null
⚠️ 严禁根据"我方进攻更多""场面占优""好像进了"来推测比分。
⚠️ 没在画面上亲眼看到数字，就必须是 null。填 null 是正确答案，不是失败。
⚠️ 也不要因为没看到进球就填 0-0——没看到记分牌一律 null。

【文字规则 · 业余场景特别说明】
- headline 必须基于视频内容写出**具体判断**（如"我方上半场高位逼抢有效"），不能写"重点已整理好"这种空话。
  → 业余球赛没记分牌、没字幕条，但**场面、节奏、配合质量你一定能看出来**，写出你的具体判断。
- highlight / weakness / next_focus 也必须具体。空话一律返空。
- 不要编造视频里没有发生的事情
- 不要在文字里提及具体比分
```

## 第 6 轮 · 动作矫正

```
你是足球技术教练。请观看这段完整比赛视频（总时长约 ${durationSec} 秒）。

${ctxPart}

【任务】针对画面中你【真正看清】的技术动作，给出动作观察与矫正建议。

可以点评的维度（只评你真看到的，没看到的绝对不要写）：
- 射门：支撑脚位置、触球部位（脚背/脚弓）、摆腿幅度、身体重心
- 传球：出球脚法、触球部位、身体朝向、力度
- 停球/接球：第一脚触球缓冲、是否停大
- 带球/过人：触球节奏、护球动作、变向
- 跑动：步频、重心、无球跑位
- 防守：上抢时机、身体姿态、卡位

【输出】只输出JSON（不要其他文字）：
{
  "techniques": [
    {
      "player_number": "10",
      "aspect": "射门",
      "observed": "你在画面里实际看到的动作（具体描述，如'禁区外右脚抽射，支撑脚离球约半米，身体后仰'）",
      "issue": "这个动作的问题（没有明显问题就填 null）",
      "advice": "具体可执行的矫正建议"
    }
  ],
  "coaching_summary": "整体动作建议（1-2句，具体，不要空话）"
}

【严格规则 · 最重要】
- 只写你在画面里【真实看到】的动作。看不清、不确定 → 该条不要输出，宁缺毋滥。
- 不要编造球员号码：看清号码就填数字字符串（如 "10"）；看不清号码就填 null，不要猜。
- 不要为了凑数而编：最多 5 条，没看清就返回空数组 []。业余球赛动作粗糙是常态，能看到能说的就列，不要全返空。
- issue 没有明显问题时填 null，不要硬挑毛病。
- advice 要具体到"怎么做"（如"支撑脚再靠近球 10-15 厘米，射门时重心前压"），禁止"加强练习""继续努力"这类空话。
```

## 上下文注入（`buildContextString`）

用户填的线索会拼在每轮 prompt 开头：

```
【额外线索】
我方队名：${ctx.team_name}          ← 若有
我方球衣特征：${ctx.jersey_hint}    ← 若有
视频开头画面中，横向 X%、纵向 Y% 附近的球员属于我方   ← 若用户点过开场位置
看不清时 team 写 null。
```

## 观察笔记（2026-09-13）

1. **反编造是这套 prompt 的核心设计**：`unconfirmed` 字段、"看不清写 null"、"返空正常"、"填 null 是正确答案，不是失败"、"严禁硬编号码"。这正是千问表现好于 Gemini 的可能原因——它放开模型说"不确定"，而不是逼它编。
2. **有轻微内部张力**：一边说"不要因为号码模糊就整个返空"，一边说"宁缺毋滥"。模型在两者间怎么取，决定了看板是"空"还是"有内容"。
3. **⚠️ 换到 qwen3.8-max 后的新风险**：该系列**默认开启思考模式**，而 prompt 里没有任何针对思考过程的约束（如"不要输出推理过程，直接给 JSON"）。若模型把 `<think>...` 一起返回，`extractJsonFromText()` 能否正确剥离就成了未知数——**这是当前最该实测的点**。
4. **成本结构**：6 轮 × 每轮整视频 = 同一段视频被计费 6 次。若能合并轮次（例如把 passes/shots/defense 合成一轮）可省约一半 token，但会牺牲单轮精度、且要重写合并逻辑。
