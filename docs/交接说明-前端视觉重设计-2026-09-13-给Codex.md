## 3. 你能拿到哪些数据（VLM 返回 → 前端类型）

后端 `mergeRoundsToDashboard` 输出 dashboard，前端 `normalizeInstantDashboard` 映射成 `InstantAnalysisDashboard`。**你设计视觉时，实际拿到的是后者**（`web/src/lib/instantAnalysis.ts`）。

### 3.1 团队模式（team）能展示的字段

| 数据 | 前端字段 | 说明 |
|---|---|---|
| 比分 | `score {home,away}` + `scoreSource` | **只认画面记分牌**，没有就是 null（不许推算） |
| 一句话总评 | `summary.overall`（=headline） | 15~35 字 |
| 团队亮点 | `summary.highlight` | 亮点第一条（最具体那条） |
| 团队不足 | `summary.weakness` | 不足第一条 |
| 下一步建议 | `summary.recommendation` / `focus` | 具体可执行 |
| 球员列表 | `players[]` | 每人：`number / role / tags[] / isMvp / insights[] / techniques[]`（字段见下） |
| 关键片段 | `events[]` | `time / clock / type / note / unconfirmed`（见第 4 节 gap） |
| 动作矫正总结 | `techniqueSummary` | 全队技术动作总建议 |

### 3.2 个人比赛（personal）能展示的字段

同上结构，但语义是「聚焦单名球员」：`summary.highlight/weakness` 是**这个人的**亮点/不足；`players[0]` 是目标球员（`isMvp=true`），可能还有 1~2 个队友；`events[]` 是**这个人参与**的关键片段。

### 3.3 ⚠️ 两个字段后端已返回、但前端还没接（重点）

1. **`strength` / `weakness`**（球员「最大亮点 / 最大不足」）：后端 `players[]` 每人都返回了（15~40 字、带具体秒数），但 `normalizeInstantDashboard` 的 `player()` 解析器**没读这两个字段**，`InstantPlayer` 类型里也没有。→ **你要展示球员「亮点/不足」，得先在 `instantAnalysis.ts` 补解析 + `InstantPlayer` 加字段**。
2. **`moments`（关键片段）**：后端团队和个人比赛都返回了 `events[]`（带 `time_seconds`，3~6 条），但前端 `InstantDashboard` 里 `showClips = mode==='training'`，而 training 已废 → **团队和个人比赛现在都看不到关键片段列表**。这是视觉重设计最该补的一块。

> 实测样本（33 秒视频，个人比赛）：players=2（8 号 MVP + 13 号，strength/weakness/insights 齐全、都带「第 N 秒」具体动作），events=5（time_seconds 10/16.5/23/25/30），比分未瞎编=null。完整样例在 `/tmp/diag_task.json`。

## 4. 当前报告页：已实现 vs 缺什么

`InstantDashboard.tsx` 一份组件按 `mode` 渲染：

- **team**（团队战报）：`MatchScoreLine` 比分条 + 「一起闪光的队友」球员网格（6 人）+ 「本场亮点 / 下次更好」两条文案。
- **personal**（个人比赛）：头像 + 评分 + 技术统计（参与/传球/射门/防守 4 格）+ 「本场亮点 / 下次更好」+ 本场特点 tags。

**已知 gap（重设计时建议一起补）**：
1. 关键片段 `events[]` 团队/个人都没展示（见 3.3）。
2. 球员 `strength/weakness` 前端没接（见 3.3）。
3. 个人比赛的「本场称号」目前没实现（产品文案里写了「本场称号」，但 `InstantPlayer.title` 一直为 null，后端也没返回称号）。
4. `InstantDashboard` 里的 `training` 分支已是死代码（训练瘦身后无人调用），重设计时可以直接清掉，别被它误导。

旧版交接说「后端完全不分模式、改 prompt 三模式一起变」。**这个坑已经修了**（commit `72a3020`）：

- **所以你现在改 prompt，只影响对应模式，不会再三模式一起变。** 但改前端视觉，跟后端 prompt 无关，基本不用碰后端。

## 7. 红线（务必遵守）

1. **UI 位置/布局由用户决定，先问再动。** 别自己拍板把某个模块从报告页挪走/删除。
2. **绝不造假数据、不做「半坏 UI」。** 数据缺失就显示诚实的空态（如「本次未识别到明确亮点」），禁止编默认文案。用户对这两条极度敏感。
3. **删除类操作先列清单**（删页面/删组件/删样式），我确认后再动。
4. **团队/个人两套进度页样式必须一致**（`InstantAnalysis` / `SingleTracking` 现在就是这个约定）。

## 8. 技术注意（开工前看）

1. **部署前端前必须 `rm -rf web/dist` 再 build**。`vite.config.ts` 有 `build.emptyOutDir:false`，dist 会堆积历史 bundle，而部署上传整个 dist。
2. **别推 GitHub、别 `git pull origin main`。** 你只在本地 commit；推送是我的活。GitHub `main` 是落后镜像（本地 origin/main 停在 8/23，还残留死文件 `web/src/lib/useDetectionFlow.ts`），拉它会污染工作区。
3. **查线上模型**：调 `haoqiu-vlm` 的 `{"selfTest":true}`，返回里有 `provider/model/modelFromEnv`（当前 `qwen3.8-flash`）。
4. 本地起 dev 看效果：`cd web && npm run dev`（沙箱内需 `env -u NODE_OPTIONS` 前缀，见协作约定文档）。
5. 后端你基本不用碰；真要动后端，改完记得 `node --check haoqiu-vlm/index.js` 验语法，且**别动 `haoqiu-vlm/node_modules`**（74MB 含 ffmpeg，线上靠它转码）。
