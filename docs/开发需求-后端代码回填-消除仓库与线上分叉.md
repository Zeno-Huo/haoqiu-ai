## 任务 4 · 回填 `index.ts` 缺失的 4 处逻辑

来源：`/tmp/online-ref/dist/index.js`（292 行），本地 `index.ts` 只有 176 行。

### 4.1 `normalizeCallEvent`（线上 86-104 行）

浏览器 SDK 的 `callFunction` 不带 HTTP 事件，且默认托管域名会遮蔽 HTTP 触发路径，所以客户端显式发一个传输信封。**必须先判 `__http`，再判 HTTP 事件特征**——顺序反了会把所有 POST 静默退化成 GET。

```ts
const normalizeCallEvent = (event: any) => {
  if (!event || typeof event !== 'object') return event
  if (event.__http === true) {
    const headers = { ...(event.headers || {}) }
    if (event.origin) headers.origin = event.origin
    return {
      httpMethod: String(event.method || 'GET').toUpperCase(),
      path: String(event.path || '/'),
      headers,
      body: event.body === undefined ? undefined
        : typeof event.body === 'string' ? event.body : JSON.stringify(event.body),
      isBase64Encoded: false,
    }
  }
  return event
}
```

在 `createHandler` 的第一行调用：`const event = normalizeCallEvent(rawEvent)`（线上 106 行）。

### 4.2 `requireWorker`（线上 166 行附近）

`/worker/*` 路由用 `requireWorker(event, config.workerToken, config.envId)` 鉴权，而不是普通用户身份。回填时保留这层，别让 worker 接口走错鉴权分支。

### 4.3 `POST /worker/v1/instant/recover`（线上 208-215 行）

```ts
const { configuredStore } = require('../haoqiu-vlm/task-store')
const ids = await configuredStore().recover(1)
await Promise.all(ids.map(id => dispatchAnalysis(id)))
return respond(200, { ok: true, recovered: ids.length })
```

前置校验：`!overrides && !process.env.VLM_WORKER_TOKEN` → 抛 `ApiError(503, 'CONFIGURATION_ERROR', 'VLM worker authentication is not configured')`。

### 4.4 `POST /api/v1/instant-analysis` 的 dispatch（线上 233-240 行）

创建成功后触发分析，**失败不能让整个请求 500**，要降级成 202 + 警告：

```ts
if (created) {
  try {
    await (overrides?.dispatch || dispatchAnalysis)(task._id)
  } catch {
    return respond(202, { ...publicTask(task), warning: { code: 'DISPATCH_PENDING', message: '任务已保存，等待恢复调度' } })
  }
}
```

（`overrides?.dispatch` 是为了测试可注入，保留这个口子。）

## 任务 5 · 行为差异对齐（3 处，前版文档漏了）

这三处不是"缺文件"，而是**同一份文件里逻辑不同**。只补前四项，接口仍然对不上。

### 5.1 任务 ID 规则：`instant_<uploadId>` → `rc_` 前缀

现状（仓库）：

- `src/service.ts:73` 生成 `const instantId = \`instant_${uploadId}\``
- `src/cos-repository.ts:78` `for (const id of [uploadId, \`instant_${uploadId}\`])`
- `src/service.ts:142` 反解 `task._id.startsWith("instant_")`

线上（`/tmp/online-ref/dist/src/service.js`）：

- 新任务统一 `rc_` 前缀；`createInstantJob` 返回 `{ task, created }`
- `taskForUser`（91-110 行）有两段 legacy 处理，必须一起回填：
  - 旧 `instant_` 任务未终态 → 返回 `LEGACY_TASK_REANALYSIS_REQUIRED`（"旧任务无法安全恢复，请创建新的分析任务"）
  - 含演示数据的旧结果 → 返回 `LEGACY_DEMO_RESULT`
- 轮询补发：`rc_` 任务且 `status === "queued"` 且创建超过 60s → 补一次 `dispatchAnalysis`（CAS 保护，不会重复分析）

### 5.1b ⚠️ 关于"统一触发入口"的红线

线上 `service.js` 实际有 **3 处** `dispatchAnalysis`，加上入口层共 4 处，作用各不相同：

| 位置 | 场景 | 失败处理 | 能否删 |
|---|---|---|---|
| `index.js:235` | 创建接口成功后触发 | 降级 202 + `DISPATCH_PENDING`（任务保留） | **保留（推荐唯一入口）** |
| `service.js:164` | `createInstantJob` 内部触发 | 抛 `503 DISPATCH_FAILED` | **可删**（与入口重复，且报错语义与"任务保留"冲突） |
| `service.js:106` | `taskForUser` 轮询补发（queued >60s） | try/catch 静默 | **绝对不能删** |
| `service.js:142` | 重复提交时 existing 仍 queued >60s 补发 | try/catch 静默 | **绝对不能删** |

106 与 142 是**防止「卡 0% / 永远排队」的唯一防线**——历史 bug 正是任务建好后从未被真正调度。CAS claim 保证任务被领走后转 `leased`，不会重复分析。**如无这两处，任务会再次永久停在 queued。**

验收时请确认：这两处补发逻辑仍在，且条件是 `status === "queued"` 且 `ageMs > 60_000`。

### 5.2 鉴权：`src/auth.ts` 缺 `requireWorker` 导出

线上 `/tmp/online-ref/dist/src/auth.js` 第 60 行定义、第 75 行导出 `requireWorker(event, configuredToken, expectedEnv)`。仓库 `src/` 下搜不到这个符号，任务 4.2 用它会直接编译失败——**必须一并回填**。

### 5.3 上传格式限制：仓库仍在拦 MP4/MOV

现状（仓库 `src/service.ts`）：

- 第 31 行 `if (!["video/mp4", "video/quicktime"].includes(contentType)) throw new ApiError(415, "UNSUPPORTED_VIDEO", "仅支持 MP4/MOV")`

## 重要原则：双向核对，不要整体覆盖

**不要**把线上包整体拷回仓库，**也不要**用仓库整体覆盖线上。两边各有对方没有的东西：

- 仓库（1322947）较新：历史删除、超时处理等
- 线上包较新：rc_ 任务体系、requireWorker、放宽的上传限制

（已核实：线上 `haoqiu-api` 包内**没有** HAI/GPU/YOLO 残留，全量搜索无命中。）

做法是**逐项比对取并集**：以 1322947 为源码起点，逐文件对照线上包，缺的补、不同的按线上行为改，仓库独有的功能保留。

另外：线上包里带 `dist/test/*.test.js`，回填后可作为测试基线参照。
